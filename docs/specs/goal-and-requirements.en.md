# Knot — A Structured List for Development Tasks

[中文](goal-and-requirements.md) | English

## Overview

A single-user desktop to-do app built specifically for managing software development tasks. At the top of the sidebar is a virtual project called "My Tasks", which holds global to-dos that do not belong to any project; below it comes the project list. A task can belong to a project (and be classified two levels deep as **Project > Module > Submodule**), or stay in "My Tasks"; the two can move into each other. Each task can also be broken down into one level of subtasks. The main view is a table grouped by module (in "My Tasks", where there are no modules, it is a flat table): modules and submodules are collapsible group rows with completion counts, and modules/submodules no longer take a column of their own (position is the classification). Tasks have a three-state status (Todo / Doing / Done) and a priority (High / Medium / Low), can be filtered by status and priority, and are sorted by priority within a group; each task can carry a free-text note. The created time is recorded automatically on creation, and the start and end times are recorded automatically as the status changes; none of them are entered manually. A new task defaults to priority "Medium" and lands in the currently selected scope (when no specific module is selected, that is "Default"), to be classified later. The interface can switch between Chinese and English, following the system language on first launch. Data is written to a local SQLite file; no account, network or server is required.

## Problem

Development to-dos are naturally hierarchical: a repository has several modules, modules contain submodules, and what you keep in your head is positional information such as "token refresh in the auth module is not done yet". A flat list loses that layer of position, so you either write a very long prefix, or a couple of days later you no longer know where the item belongs; and with an all-in-one project management tool, you first have to sign in, create a workspace and configure fields, and the cost of recording one task far exceeds the task itself.

At the same time, one piece of work has steps inside it ("implement token rotation" contains "handle concurrent refresh" and "add expiry test cases"), and work has weight (which one comes first). If this information can only go into the task title, the title balloons into a one-sentence essay.

What is needed: enough structure to express "Project / Module / Submodule + one level of subtasks", three levels of weight, and input fast enough — one line and Enter, by default not asking where it belongs, then classify, break down and raise priority as needed.

## Capabilities

- **Project / Module / Submodule hierarchy** — You can create multiple projects; under each project you can create modules, and under modules submodules (at most two levels of nesting). All three levels can be created, renamed and deleted in the UI, and **the entry points are unified in the sidebar**: project name right-click → New module / Rename project / Delete project; module row right-click → New submodule / Rename module / Delete module; submodule row right-click → Rename / Delete; **right-click on empty sidebar space** → New module (lands in the current project, saving you from first finding the right project name). Module names must be unique within a project (compared exactly after trimming; project and submodule names are not restricted yet). All renames use **in-place editing**: after double-clicking a project / module / submodule name, the name itself becomes an input, with no dialog; Enter or blur saves, Esc cancels, and an empty or unchanged value is restored.
- **Sidebar: My Tasks + project list** — The top of the sidebar always has a fixed "My Tasks" row (a virtual project that always exists, cannot be deleted and has no modules); below it come the "Projects" section and the project list. Clicking an item switches to that view. The native context menu is globally disabled by default, with the custom menus on sidebar project names, scope nodes and empty sidebar space as the only exceptions; double-clicking a project, module or submodule name does an in-place rename, while a single click still switches the view. The right edge of the sidebar can be dragged to resize it (180–420px, leaving at least 360px for the main area); the width is stored locally and reused on the next launch. **Modules can be dragged up and down to reorder**: hold and drag a module row; whether the pointer lands on the upper or lower half of an adjacent module decides whether it is inserted before or after it, and an indicator line appears at the drop point; releasing writes it locally immediately, and both the sidebar and the table grouping reorder together. Submodules move with their module and are not sorted on their own; "All" and "Default" are fixed scopes and do not participate in dragging.
- **New project** — Clicking "+ New project" expands an input row below the project list; Enter creates the project and switches to it. Clicking anywhere outside the form or pressing Esc **collapses and clears** it, returning to the unopened state (typed text is discarded; this is a lightweight one-line entry point that keeps no half-open draft).
- **Scope tree** — Under a project you can expand the module/submodule tree; clicking a node limits the main view to that subtree, and "All" and "Default" are also selectable nodes. The count on a node is the subtree's `done/total`. The selected node becomes the root of the view: when a submodule is selected it is no longer indented itself. "My Tasks" has no such tree.
- **Adding tasks** — Type a line of text and press Enter to add it to the **current scope**: when the scope is a module/submodule, the new task lands in that module/submodule; when the scope is "All" or "Default", it lands in "Default"; in "My Tasks" it becomes a global to-do with no project. The input placeholder follows the scope (e.g. `Add to "Auth"`), so you know where it will land before pressing Enter. The default priority is "Medium", and the task is placed at the end of its group.
- **Subtasks** — Any task can be broken down into **one level** of subtasks (a subtask cannot have subtasks). The entry point is the "+" on the parent task row: clicking it opens an input row in place below the parent task; Enter saves and lets you keep adding the next one, Esc cancels, and blur saves non-empty content. A subtask inherits its parent's module/submodule classification but has its own priority and note. **A subtask's priority cannot be higher than its parent's**: when the parent is "Low", a new subtask is also "Low"; when the parent is lowered, subtasks still above it are lowered too. The parent task row has a collapse arrow and is expanded by default; subtasks render below it as rows indented by 4 spaces, with no prefix symbol. After the parent task title, the subtask completion count `done/total` is shown; the count covers all subtasks and does not change with filters. **The parent-child relationship can be converted both ways**: right-clicking a top-level task offers "Demote to subtask…", listing the other top-level tasks in the current container (grouped by Default / module / submodule; within a group, unfinished / doing first and done after, ordered by creation time ascending within the same status); the chosen task becomes a subtask of the target, its module/submodule is cleared, it is placed at the end of the target's subtasks, and if its priority is higher than the new parent's it is reduced to the parent's level. A parent task with subtasks cannot be demoted directly; its subtasks must first be deleted or promoted. Right-clicking a subtask offers "Promote to top level", which clears the parent task, inherits the original parent's module/submodule and places it at the end of that top-level group. A subtask also has "Move to…": it lists the other top-level tasks in the same container (excluding the current parent and completed tasks; targets may be parents that already have subtasks or leaf tasks without any); choosing one retargets the subtask under it, clamps its priority to the new parent's level, and re-aggregates both the old and the new parent. Both cases recompute the affected parent task's status and show the usual toast.
- **Parent-child status aggregation** — When all subtasks are done, the parent task is not written directly; instead a dialog asks whether to mark the parent as done too (Confirm / Cancel). Only after confirmation is the parent written; cancelling leaves it unchanged. As soon as any subtask enters doing or done (but not all are done), the parent automatically becomes doing; when all subtasks are in the Todo state, the parent automatically becomes Todo. Conversely, marking as done a parent task that still has unfinished subtasks first shows a confirmation dialog (the button is "OK"), and on confirmation the subtasks are completed along with it. When a parent task is manually moved back, its subtasks do not change ("subtask progresses → parent doing / all subtasks done → parent completion needs confirmation" is a derivation triggered by events, not an invariant that always holds); a parent automatically moved to doing / Todo produces a toast that disappears after 3 seconds, while parent completion uses a confirmation dialog rather than a toast. When several notices appear at once they are queued in arrival order instead of replacing one another. Deleting subtasks also triggers the derivation: after deleting the last unfinished subtask, if the remaining subtasks (possibly zero) are all done, the same dialog asks whether to complete the parent.
- **Table (main view)** — One row per task, **always grouped by module**; there is no grouping selector in the UI. Unclassified tasks are gathered into a "Default" group placed before the module groups. Modules and submodules are collapsible group rows with counts (e.g. `3/7`, `2 submodules`); the counts **include parent tasks only**, not subtasks. Modules/submodules do not take a separate column — position is the classification. In the "My Tasks" view there are no modules, hence no group rows, and the table is simply a flat list. The table draws no cell borders; columns and rows are distinguished only by alignment, whitespace and hover background, with a single divider kept below the header; dragging a header divider changes the columns on both sides (hovering highlights both headers, dragging shows the current widths of the two columns), and once one side reaches its minimum width, continuing to drag **pulls along the neighbouring columns on that side**; the Task column always absorbs the remaining width. Adjustments are remembered locally and still apply on the next launch. **The Task column wraps automatically according to column width**: a long title (including long English text or links without spaces) wraps to the next line, the row height grows with the content, and the parent task's collapse arrow, count and "+" stay on the first line; the other columns stay single-line.
- **Status (three states)** — Todo / Doing / Done. Clicking once in the status cell cycles through the three states (an empty box / a half circle / a check), which suits moving forward in order; to jump directly to a status, use "Set status…" in the task row's right-click menu, with the current status checked. There is no separate checkbox for status — one field has only one primary control. Both entry points go through the same "first decide whether confirmation is needed, then write" flow: marking as done a parent task that still has unfinished subtasks still shows a confirmation dialog first.
- **Priority** — High / Medium / Low, default "Medium". It is a column in the table; clicking in the cell opens a **three-level popover** to pick one, distinguished by color. Why it differs from status: status has a natural three-state order, so the status cell uses cycling for quick advancement (to specify directly, use the right-click menu); priority is a choice among three levels, and cycling would add an extra step going from Low to High, so a popover is used.
- **Sorting** — The headers of the priority / created / start / end columns have sort buttons to their right: one click ascending, another descending, a third restores the default. By default (no column sort), within each group tasks are first split into two by status: unfinished / doing first, done after (when the Done filter hides done tasks, only the first group is visible); within each group they are ordered by priority High → Medium → Low, and by creation time ascending within the same priority (earlier creations on top; old tasks with no recorded creation time count as the earliest). Once a column is selected, the whole group is sorted only by that column and done tasks are no longer moved to the end; equal values fall back to creation time and insertion order. Start / end times that are not recorded go last in either ascending or descending order. The group structure is always preserved: parent tasks are sorted first, and within each parent its subtasks are sorted by the same rules; subtasks are never split off. Changing priority moves the row, which is the price of sorting; the moved row **along with its following subtask rows** briefly highlights for 1 second at the new position, so that a row does not "jump away and get lost". Moving to another group via "Move to…" highlights the same way.
- **Filtering** — Two groups of checkable chips at the top, applied together with the sidebar scope:
  - **Status**: Todo / Doing / Done, with only the first two checked by default (i.e. "what is left to do"). Unchecking "Done" hides done tasks.
  - **Priority**: High / Medium / Low, all checked by default.
  - **Parent-child filtering**: parent tasks and subtasks are evaluated separately against the same set of conditions. When a parent task does not match but a subtask does, the matching subtask is still shown, with the parent task as a greyed-out context row; the whole tree is hidden only when neither matches.
- **Appearance of done tasks** — When the "Done" chip is checked, done rows stay in place with greyed text and a strikethrough; when it is unchecked the rows disappear, but the counts on group rows and in the sidebar scope tree are still based on all tasks (e.g. `3/7`), so users do not think tasks were lost. When a task has just been marked done and therefore leaves the current view, a 3-second toast at the bottom explains that it was completed and hidden; the toast does not include the task title.
- **Classification and cross-container moves** — The "Move to…" item in a task row's right-click menu is a "My Tasks / project / module / submodule" tree that works both ways: a task in My Tasks can be dispatched into a project's module, and a task in a project can be sent back to My Tasks. Subtasks do not take part in the "Move to…" container/classification move, but they can be retargeted to another top-level task inside the same container; right-clicking a top-level task shows "Set status… / Move to… / Demote to subtask… / Delete task", and right-clicking a subtask shows "Set status… / Move to… / Promote to top level / Delete task". Delete items are separated from the operations above by a divider.
- **In-place task text editing** — Double-clicking task text (parent tasks and subtasks alike) turns it into a **multi-line text box**: the width matches the title cell, the text wraps with the column width, the height grows automatically with the content, and the wrapping matches what the read-only state shows; the input replaces only the title itself, its left edge aligned with the text before the double-click and its right edge aligned with the right side of the title cell; the parent task's collapse arrow stays in place, while the subtask count and "+" temporarily give way during editing; Enter saves, Esc cancels; if the content is empty or only whitespace on save, the original text is restored and nothing is written. Line breaks in pasted text are folded into a single space before saving — line breaks are only for display, and the title itself remains single-line text. **Clicking elsewhere (blur) is equivalent to pressing Enter to save** — moving focus is the most common "I'm done editing" in a table, and losing typed text is worse than saving once too often; Esc remains the only "discard". Notes do not use this path and are still edited in a dialog.
- **Note** — A single-line truncated summary column in the table; clicking the cell opens a dialog to view and edit arbitrary text. Both parent tasks and subtasks have notes.
- **Created time** — When a task is created (parent tasks and subtasks alike), the current time is recorded automatically, and it never changes afterwards. The "Created" column in the table is a read-only summary, shown as `2026/11/04 09:00` (24-hour clock) in both Chinese and English; old tasks created before this column existed have no creation time and show `—`.
- **Start / end times (recorded automatically with status)** — Every task (parent tasks and subtasks alike) automatically maintains two times when its status changes, to the minute, with no manual entry in the UI:
  - Entering **Doing**: if the start time is empty, record the current time; clear the end time.
  - Entering **Done**: record the current time as the end time; the start time stays unchanged.
  - Returning to **Todo**: clear both; this round is void, and entering Doing again records a new start.
  - Writing the same status again does not overwrite existing times; when a parent task is changed automatically by aggregation, the same three rules apply.
  - After priority in the table come three read-only summary columns, "Created", "Start" and "End", localized according to the current UI language when displayed, showing `—` when not recorded. Storage and sorting still use the fixed text `YYYY-MM-DDTHH:MM`; the times are shown as information only and do not participate in sorting, filtering or counting.
- **Deletion** — Deleting a task (together with its subtasks) is in the task row's right-click menu; deleting a module/submodule or a project is in the sidebar project's right-click menu. Deleting a module/submodule deletes the tasks inside it as well; deleting a project deletes all tasks in the project. Both first show a confirmation dialog stating the number of affected tasks. If after deletion the view is still on the deleted task scope: deleting a module/submodule returns to the project's "All", and deleting a project returns to "My Tasks". Deleting subtasks also derives the parent task's status under the aggregation rules and shows a toast as needed.
- **UI language** — The status bar offers a three-state switch "中文 / English / System", built the same way as the theme button; first launch defaults to following the system (`navigator.language` starting with `zh` means Chinese, otherwise English), the choice is stored locally and reused after a restart. After switching, the whole UI re-renders immediately and `<html lang>` updates accordingly; project/module/task names entered by the user are data and are not translated. Backend errors, confirmation reasons and aggregation notices also follow the UI language.
- **Local persistence** — Every change is written immediately to the local SQLite file; after restarting the app the structure and content are unchanged.
- **Data safety** — A backup is generated automatically before the database schema is upgraded (only the latest 5 are kept); if migration fails, the app refuses to start, shows the reason and the backup file path in the window, and the database stays at the version before the upgrade instead of being half-modified. Development builds provide a "Reset database (dev)" entry; release builds have no such path.

## Trade-offs in the display form

The main view went through one round of choosing among "pure table / pure tree / a hybrid of the two", and the conclusion is a **grouped table**:

- A pure table (classification only as columns) has a weak sense of hierarchy; the structure can only be seen in the sidebar tree;
- a pure tree (classification as indentation) degenerates into an indented flat list when a single module has many tasks, loses column alignment, and makes cross-module comparison hard;
- a tree table (modules themselves as table rows) keeps the columns, but most cells of a module row are empty, indentation eats into column width, and the number of rows grows noticeably;
- **a table ⇄ tree dual-view switch** is explicitly out of scope: it means maintaining two layouts and two sets of collapse states, plus syncing filters and selection; in the end both views are half-finished.

The grouped table stuffs the tree into a table with "the module is the group row": classification is expressed by indentation and group rows, and the columns keep only the information that really needs alignment — status, task, priority and note. This also turns "should done tasks be greyed out or hidden" into the result of a single control, instead of two switches that fight each other. Likewise, the primary control for the three-state status remains the cycle, with no separate checkbox kept; to specify a status in one step, use the task row's right-click menu.

The grouper was removed later: the only classification dimension that is a real requirement is "by module" (filtering by status is enough for seeing status), and one more selector means one more set of states and one more rendering branch to maintain. The cost is losing the ability to "show a flat, ungrouped list and compare unfinished work across modules horizontally" — when you need that comparison, use filters together with the group-row counts.

## Non-Goals

- Multiple users, accounts, cloud sync — this is a single-user local tool.
- A cross-project master table — there is no view that gathers the tasks of all projects into one table; "My Tasks" only holds tasks that belong to no project and does not aggregate the content of each project.
- Task search — not in this round; grouping and filtering are enough to locate things.
- Drag-and-drop classification — classification always goes through the task row's right-click menu.
- Subtasks of subtasks — only one level is allowed.
- Subtask completion counts (such as `1/2` on a parent task row) — there are not many subtasks, and expanding the parent task shows them.
- Switchable grouping dimensions (group by status / flat without grouping) — the view is always grouped by module, and status is handled by filtering.
- Custom priority levels or custom status values — the three states and three priority levels are a fixed vocabulary.
- Reminders, calendar sync, duration statistics or sorting by time for time fields — start / end times are only recorded and displayed as information.
- A third language, RTL layout — only Chinese and English in this round; no right-to-left layout is introduced, and the sorting of tasks/modules does not change with the language.

## Tech Notes

| Aspect | Choice | Reason |
| --- | --- | --- |
| App shell | Tauri 2 (Rust) | Installer size and memory use are far lower than Electron; a desktop app only needs a thin shell |
| Frontend | Vite + TypeScript, native DOM, no UI framework | The UI is still "one table + one grouper + one sidebar"; the build and dependency cost of a framework outweighs the benefit (my judgment, not something you specified; can be overturned) |
| Data storage | SQLite, in the application data directory (Windows: `%APPDATA%/knot/tasks.sqlite`) | The option you chose: zero interaction, no fear of loss, and room left for a growing number of tasks later |
| Data access | Tauri commands + `rusqlite`; the frontend never touches the database directly | Data reads and writes are centralized in one place, with a single path for permissions and migrations |
| Data model | `project` → `module` → `submodule` → `task`; `task` holds `status` (Todo/Doing/Done), `priority` (High/Medium/Low), `note`, `sort_order`, `project_id` (**nullable; empty means it belongs to "My Tasks"**), `module_id`/`submodule_id` (nullable = Default), `parent_id`/`parent_task_id` (nullable = top-level task; one level only) | The hierarchy is only two classification levels + one level of subtasks, so foreign keys are much simpler than a generic tree structure; "My Tasks" is not a real project row but is expressed by an empty `project_id`, saving a system record that would always exist |
| Grouping, filtering, sorting | All done in the frontend over already-fetched tasks, not persisted | The task volume of a single project is small locally; frontend computation is fast enough and avoids writing a query for every grouping × filter × sort combination |
| Internationalization | Hand-written typed dictionaries (`src/i18n/`) + `Intl`; the backend returns `{ key, params }` and the frontend translates | Only two languages; the dependency and build cost of an i18n framework outweighs the benefit; the backend is decoupled from language, and tests assert keys rather than sentences |
| Target platform | Windows first | You develop and use it on this machine; Tauri makes macOS/Linux basically free, but it is not specifically verified for now |

## Alternatives Considered

There are already a number of local-first desktop to-dos in this space, but they either have grown into a full system or live elsewhere:

- **Super Productivity** ([repo](https://github.com/super-productivity/super-productivity)) — a mature local-first product with timeboxing, a Pomodoro timer, Jira/GitHub integration and a plugin system. Its complexity is exactly what this project wants to avoid: what is wanted is "open it and record a line".
- **Vikunja** ([repo](https://github.com/go-vikunja/vikunja)) — the most feature-complete self-hosted to-do, but it needs a server and deployment, which is the opposite of the "offline, no deployment" premise.
- **A batch of Tauri + React + SQLite imitations** (such as [mbenja/tauri-todo-app](https://github.com/mbenja/tauri-todo-app), [Tanveer-LowCoder/To-Do-MCP](https://github.com/Tanveer-LowCoder/To-Do-MCP)) — the tech stack is the same, but they are all flat lists with no project/module/submodule structure and no grouped table or subtasks.
- **Taskwarrior** ([site](https://taskwarrior.org/)) — extremely capable (with priorities and dependencies), but command-line only; the requirement is a desktop window with a grouped table.

Conclusion: this idea is not fully covered by existing projects, but its value lies only in "being small enough" — before adding any new capability, ask yourself whether it is sliding toward Super Productivity.
